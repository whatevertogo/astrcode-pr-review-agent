# 定向阶段：确定本次审查的问题

根据已有 PR 元数据、文件清单和检查记录，确认行为变化及需要追踪的入口、消费者和约束。区分机械搬移与行为变化，选择适用的审查分块。

按实际行为变化提出调查链，而不是按目录罗列文件：入口 → 状态或接口变化 → 生产消费者 → 失败/取消路径 → 测试或操作说明。相关文件可以没有修改；只在需要确认关联时读取源码，具体候选的深入验证留给后续阶段。小改动一条链即可，不要求凑数量。

每条调查链可输出一个 `<review_chain>` 块，块内是 JSON：`{"behavior":"这次改变了什么行为","changed_paths":["变更清单中的精确路径"],"related_paths":["需要追查的仓库内路径"],"checks":["需要核实的具体契约或反例"]}`。JSON 协议下使用 `review_chains` 数组。链是待核实线索，不是发现；不要把它当作已审覆盖。无法可靠分组时省略，插件仍会安排所有变更文件。

最多留下 5 条含代码位置的可复用事实或明确待核对的前提；事实写入 investigation_log，待核实前提写入 observation。不要重复完整文件清单或 PR 描述，不因改动量大而推断风险高。

除非现有证据已满足候选证据要求并能准确定位，否则不产出 finding。未完整检查文件时不声明 files_reviewed。不自行发布评论。
