# 定向阶段：确定本次审查的问题

根据已有 PR 元数据、文件清单和检查记录，确认行为变化及需要追踪的入口、消费者和约束。区分机械搬移与行为变化，选择适用的审查分块。

按行为变化提出调查链，而不是按目录罗列文件。一条链对应一个可独立判定的行为变化，按 入口 → 状态或接口 → 生产消费者 → 失败/取消路径 → 测试或操作说明 展开；不同行为分开写，链之间可以共享 `changed_paths`（插件会合并为同一工作单元）。相关文件可以没有修改；只在需要确认关联时读取源码，具体候选的深入验证留给后续阶段。未列入任何链的变更文件仍会按常规分片审查，不需要为覆盖凑链。

需要留下线索时，每条链输出一个 `<review_chain>` 块。标签为单数，块内只放一个 JSON 对象，不加代码围栏：

<review_chain>
{"behavior":"一句话描述改变的行为","changed_paths":["清单中 kind=code、docs 或 oversized 的精确路径"],"related_paths":["仓库相对路径"],"checks":["可判定的核实问题"]}
</review_chain>

`changed_paths` 只填清单中 kind 为 code、docs 或 oversized 的路径，不带反引号、行号或说明；generated 与 no_patch 文件只能写进 `related_paths`。`related_paths` 用仓库相对路径，不要绝对路径、`..` 或反斜杠，只列真正需要打开的路径。`behavior` 一句话，`checks` 至多 3–5 条；所有链合计受请求预算限制，超出的链会被丢弃。链是待核实线索，不是发现，也不算已审覆盖。已进入 `checks` 的疑点不要重复写进 observation。

最多留下 5 条含代码位置的可复用事实或明确待核对的前提；事实写入 investigation_log，待核实前提写入 observation。不要重复完整文件清单或 PR 描述，不因改动量大而推断风险高。

除非现有证据已满足候选证据要求并能准确定位，否则不产出 finding。未完整检查文件时不声明 files_reviewed。不自行发布评论。
