# 审查报告表达示例

以下均为虚构场景，只示范面向维护者的语气和结构，不是实测结论，也不是协议样例或模型评分。示例省略了程序添加的 marker、身份行、SHA、执行信息等内容。

## 初审：发现明确问题

本次改动把消息发布放到了任务写入之前。消费者收到消息后会立即查库，查不到就丢弃，所以数据库里可能留下从未执行的任务。

需要先处理：

- `src/enqueue.rs:48`：`publish(id)` 现在在 `insert_job(id)` 之前执行，使这个时序窗口变得可达。
- 证据：`worker.rs:70` 在查不到任务时直接返回，没有重新入队。
- 建议：先完成任务写入再发布消息，并用一个“发布时立即消费”的测试固定顺序。

覆盖与限制：已审文件见折叠区；尚未运行并发复现，以上结论来自源码路径推导。

## 复审：回应上轮意见

上轮提到的“失败后无法重试”已经消除：调用方现在每次请求前都会重新初始化，`retry.rs:22` 的测试覆盖了首次失败后的第二次调用。本轮没有发现新的阻塞问题。

仍有一项待确认：取消路径是否保证旧写入者退出，现有代码只看到调用方会等待，但缺少取消后立即替换的断言。详见待核实观察。

## 需决策：产品或契约取舍

当前实现删除了旧配置项，仓库内调用方已经迁移，但现有材料没有明确的外部兼容承诺。这不是已确认的运行时缺陷，需要由维护者决定是否保留兼容入口。

如果仍支持未迁移的外部调用者，应提供迁移期或兼容读取；如果已经决定移除，建议在发布说明里写清影响范围。结论不表示已经获得批准或可以合并。

## 验证不足

这次改动没有提供延迟基准，静态阅读无法判断性能是否退化。覆盖范围未记录，尚不能确认所有文件都已审完；`cargo test` 有 1 项检查失败，不能把验证视为通过。先记为待核实：需要同一数据集下的前后对比和语义等价检查，才能确认性能主张。

在补齐这些证据前，不把缺少测试或基准写成已经发生的故障，也不据此宣称改动有效率提升。失败检查、未执行检查和未记录的覆盖范围分别说明，不合并成一句“验证不足”。
